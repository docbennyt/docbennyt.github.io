Your API response hasn’t read your TypeScript types

A successful request can still return the wrong shape. Here’s a small parser for the boundary and the requests I’d test around it.

By Benedictus Makuyana18 November 2026

Your editor says title is a string. The server sends null. Both can be true if you asserted a type without checking the actual response. TypeScript types disappear at runtime; JSON still needs validation.

THE BOUNDARY RULE

Treat data from a network, file or user input as unknown until runtime checks prove the shape you need.

1. Validate at the boundary

Keep the check close to the code that receives the response. If the screen only needs a session title, validate that field instead of pretending the whole server response matches a TypeScript interface.

2. Return a shape the UI can trust

Here is a deliberately small parser. It accepts an object with a non-empty title and returns only the field the caller needs. A missing, empty or non-string title is rejected before it reaches the component.

type Session = { title: string };

function parseSession(value: unknown): Session {
  if (
    typeof value !== "object" ||
    value === null ||
    !("title" in value) ||
    typeof value.title !== "string"
  ) {
    throw new Error("Expected a session title");
  }

  const title = value.title.trim();
  if (!title) throw new Error("The session title is empty");

  return { title };
}

async function loadSession(url: string): Promise<Session> {
  const response = await fetch(url);
  if (!response.ok) {
    throw new Error("Request failed: " + response.status);
  }

  const payload: unknown = await response.json();
  return parseSession(payload);
}

There are separate failure points here. A request can return an HTTP error such as 404, and a successful response can still contain invalid JSON or an unexpected shape. Keep enough detail in your logs to distinguish them, while showing the user a clear message and a way to retry. For larger nested objects, use a runtime schema validator at the same boundary.

3. Test the data and the request

01Valid dataA title with extra spaces is trimmed
02Bad shapeTry null, a missing field and an empty title
03Bad requestTry a 404 and invalid JSON

At screen level, check that the student can tell what happened and retry without starting again. A parser test proves the boundary; a UI test proves the recovery path.

PUT IT INTO PRACTICE

One rule for every API call

  • Mark untrusted payloads as unknown.
  • Validate required fields once at the boundary.
  • Keep HTTP, parsing and validation failures distinguishable in logs.
  • Give the user a clear error and a recoverable next step.
