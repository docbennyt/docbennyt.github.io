Your API response hasn’t read your TypeScript types

A successful request can still return the wrong shape. Here’s a small parser for the boundary and the requests I’d test around it.

By Benedictus Makuyana18 November 2026

In this article

  • A parser you can read at a glance
  • Test the boundary and the screen
  • Sources

Say your timetable screen needs a class name. The API returns {"title":"Databases"}, the component trims the title, and everything looks good. Next week the response is {"title":null}. If you asserted the type of the response, the editor still sees a string. The browser has a different opinion.

I’d put that disagreement in one place: the function that receives the response. The TypeScript handbook calls the process of refining a type through checks narrowing. Start with unknown at the boundary and return a smaller shape once the checks pass.

A parser you can read at a glance

Here’s a deliberately small example. The valid response has a title with at least one non-whitespace character. Additional fields can come through the API and are ignored here because the caller only needs the title.

type Session = { title: string };

function parseSession(value: unknown): Session {
  if (typeof value !== "object" || value === null ||
      !("title" in value) || typeof value.title !== "string") {
    throw new Error("Expected a session title");
  }

  const title = value.title.trim();
  if (!title) throw new Error("The session title is empty");
  return { title };
}

async function loadSession(url: string): Promise<Session> {
  const response = await fetch(url);
  if (!response.ok) throw new Error("Could not load the session");
  const payload: unknown = await response.json();
  return parseSession(payload);
}

Two kinds of failure are easy to blur together. Fetch can resolve with an HTTP error such as a 404, so check response.ok. Parsing JSON can fail even after a successful HTTP response. The UI can offer one plain message with a retry while the app records enough detail to tell those cases apart. Keep a valid empty result separate from a request that failed.

Test the boundary and the screen

I’d test the parser with a padded title, an empty title, null, and a missing field. At the request boundary I’d add a 404 and a response that claims success but sends invalid JSON. At the screen level I’d check the part a student cares about: can they tell what happened, and can they try again without starting over?

For a bigger shape with nested data, I’d move to a runtime schema and keep it at the same boundary. If you use an AI tool to write the schema, hand it a representative payload plus the broken cases first. A perfectly plausible type assertion takes one line. A failing payload is what tells you whether the generated code made a useful change.
