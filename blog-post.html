Give your coding agent a failing test and a smaller job

A practical loop for AI-assisted development, with one workflow to verify and two studies that explain why I measure the whole job.

By Benedictus Makuyana18 November 2026

In this article

  • Give it an observable finish line
  • Measure from brief to verified change
  • Read the change before you commit it
  • Sources

A coding agent will happily give you a whole settings page when all you needed was for the save button to recover from a failed request. You now have more code to read, more states to check, and the original bug somewhere in the middle. I’d begin by making the failure cheap to see.

Imagine a staff member edits a booking note and loses their connection just before saving. The useful behavior is specific: keep the draft, show that saving failed, and allow another attempt. Write that behavior in the issue, alongside the steps that reproduce the failure. Add a regression check if the repository supports one. Give the agent the issue and the smallest relevant area of code.

Give it an observable finish line

My handoff would include the expected behavior, the place where the current save flow lives, and the command for the focused check. I’d ask for the change plus the test result. If the agent discovers it needs to touch a shared persistence layer, I’d inspect that dependency before letting the patch grow. The larger the diff gets, the more time I spend learning what changed.

Playwright’s guide recommends testing user-visible behavior. For this example I’d check that the typed note survives the failed request, then that a successful retry displays the saved note. A test that only checks whether a state variable became true skips the part the staff member sees. Run the test against the original code too so you know it actually catches the failure.

Measure from brief to verified change

Peng and colleagues reported that participants with GitHub Copilot completed a prescribed JavaScript HTTP server task faster in their experiment. METR’s early-2025 randomized study reported that experienced open-source developers took 19% longer when using AI tools on tasks in repositories they knew. METR treats that result as a snapshot and links to a later update. The tasks, participants, tools, and conditions differed. Those studies give me a reason to watch my own review and rework time closely.

For a week, keep a rough log of three things: time to define the job, time to review and test the change, and time spent fixing anything missed. Try the same categories on work you do manually. One week of varied tasks can reveal where your own time goes, even though it can’t isolate the effect of the tool. A fast first patch is welcome. I care about how long it takes me to trust the result.

Read the change before you commit it

The final pass is a boring one. Check what happens on the second click. See whether the error message is reachable with the keyboard. Look for unrelated edits and make sure the test covers the original scenario. If you can explain why the draft survives the failure and show the retry working, the agent has helped you deliver something you can stand behind.

Sources

  • Playwright — Best practices for user-visible behavior
  • Peng et al. — Experimental study of GitHub Copilot and developer productivity
  • METR — Randomized study of early-2025 AI tools and experienced open-source developers
