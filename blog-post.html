Give your coding agent a failing test and a smaller job

A practical loop for AI-assisted development, with one workflow to verify and two studies that explain why I measure the whole job.

By Benedictus Makuyana18 November 2026

#AI-Agents#Code-Review#Testing#Developer-Tools

In this article

  • Give it an observable finish line
  • Measure the whole job
  • Review the patch like you own it
  • Sources

An agent can say “done” while the original bug is still there. The useful question is not how much code it produced. It is whether a person can complete the task that was failing before.

THE RULE

Give the agent a reproducible failure, a narrow change and a check that proves the user-facing behaviour.

1. Give it an observable finish line

Imagine a staff member edits a booking note and loses the connection just before saving. “Make saving robust” is too vague. Write the expected behaviour instead: keep the draft, show that saving failed and let the staff member retry without typing everything again.

Give the agent the reproduction steps, the relevant save flow and the command for the focused test. Ask it to change that path and report what it ran. If it discovers that a shared persistence layer must change, pause and inspect that dependency before the patch grows.

01ReproduceShow the failure on the original code
02ConstrainName the expected behaviour and files
03VerifyRun the regression check and inspect the diff

Playwright recommends testing what users can see and do. For this example, check that the note survives the failed request and appears after a successful retry. Run the test against the original code too; otherwise you do not know whether it catches the bug.

2. Measure the whole job

Productivity studies do not produce one universal speed score. Peng and colleagues reported that participants using GitHub Copilot completed a prescribed JavaScript HTTP-server task 55.8% faster in their controlled experiment. METR’s 2025 randomized study found that experienced open-source developers took 19% longer on tasks in familiar repositories when using the early-2025 AI tools they studied. The tasks, participants and tools were different, so those results should not be compared as if they were the same experiment.

There is an important update. On 24 February 2026, METR said its later experiment could not provide a reliable estimate of the current productivity effect. Developers were increasingly selecting which tasks they submitted and whether they would work without AI; the team also identified timing problems when people ran multiple agents. METR thought developers were probably getting more speed-up from AI by early 2026, but said its data was weak evidence for the size of that effect. The 19% result is a historical finding, not a claim that AI makes every developer slower today.

For your own work, log the time spent defining the task, reviewing and testing the patch, and fixing anything missed. Compare similar tasks rather than one easy AI task with one difficult manual task. A small personal log cannot prove causation, but it can show where your time is actually going.

3. Review the patch like you own it

Check the second click, the failed request, the keyboard path and any unrelated files that changed. Read the test and make sure it would have failed before the fix. If you cannot explain why the change works, ask for a smaller explanation or inspect the code yourself. The commit is yours, even when an agent wrote the first draft.

PUT IT INTO PRACTICE

Try this on your next task

  • Write the expected behaviour in one sentence.
  • Give the agent a reproduction and a focused failing test.
  • Ask for the smallest patch and the exact test command.
  • Read the diff and rerun the check before committing.
