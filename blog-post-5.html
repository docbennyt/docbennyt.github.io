Will that timetable open on a student’s phone?

CalenderZW starts with a familiar Zimbabwean campus problem. The useful test is what happens after somebody sends the timetable to a classmate.

By Benedictus Makuyana18 November 2026

In this article

  • Make uncertainty visible before import
  • Test the exported file in a real calendar
  • Keep the page light enough to share
  • Sources

A student sends a timetable to a class group. Somebody opens it just to find the first lecture on Monday. They have a small screen, a full group chat, and about thirty seconds for your software. This is the situation I have in mind with CalenderZW. A timetable has done a useful job when people can tell where they need to be and when.

I build from Zimbabwe, so this is a problem close to the work in my portfolio. The point of testing with a smaller phone and an intermittent connection is to see which decisions hold up for the people using the tool. Start with a real sample, with any personal information removed, then try to finish the task on the device you’d bring to class.

Make uncertainty visible before import

A heading that looks like a room number might be a course code. A timetable can include a date range for the term without repeating it under every row. Even a clean-looking time can leave you unsure whether a session crosses midday. Use a preview to show what the app thinks the input means. Put unmapped lines beside the preview so a student can correct the data before it goes into a calendar.

I’d put three samples in a test fixture: a regular weekly timetable, one with an incomplete row, and one with two sessions at the same time. The first should stay quick to import. The second needs a way to see what was skipped. The third deserves a visible conflict and a chance to review both entries.

Test the exported file in a real calendar

The iCalendar standard gives events identifiers through UID and describes recurrence and time-zone semantics. For a weekly class, choose how you’ll express its start time and when recurrence ends. If you publish a feed, keep a stable identifier for the same class event across updates and test how your supported clients handle changes. If you offer a downloadable file, try importing it twice and see what each client does. Duplicate behavior can vary by client and import workflow.

Check the first week, last week, and a moved session in the actual calendar UI. Test from a phone set to a different time zone. Confirm that a course’s schedule still represents the intended local time. Also keep the web view usable on its own. Some students will just open the page and screenshot it.

Keep the page light enough to share

Start with the timetable text. Reserve space for any screenshots and send smaller assets to smaller screens with responsive images. Test a cold visit under throttling and compare the bytes sent before the timetable becomes readable. On a connection that drops midway through, the problem you’ll notice first is simply that Monday never arrived.
