Will that timetable open on a student’s phone?

CalenderZW starts with a familiar Zimbabwean campus problem. The useful test is what happens after somebody sends the timetable to a classmate.

By Benedictus Makuyana18 November 2026

#EdTech#Calendars#Mobile-UX#Zimbabwe

In this article

  • Preview before you import
  • Keep calendar events stable
  • Test the share path
  • Sources

A student sends a timetable to a class group. Someone opens it to find Monday’s first lecture. They have a small screen, a busy chat and about thirty seconds. The product has to make that first answer easy to find.

STUDENT-FIRST RULE

Do not turn an uncertain timetable into calendar events silently. Show the student what was understood and let them correct it first.

1. Preview before you import

A heading that looks like a room number might be a course code. A term date range may apply to every row without being repeated. A time can be valid but still ambiguous if the source omits whether a session is before or after midday.

Show a preview of the sessions the app has parsed. Put lines it could not map beside the preview so the student can correct them before export. Keep three sample inputs in your tests: a regular weekly timetable, an incomplete row and two sessions at the same time. The first should import quickly; the second should show what was skipped; the third should make the conflict visible.

2. Keep calendar events stable

The iCalendar standard uses a UID to identify an event and defines recurrence through properties such as RRULE. Time-zone information matters too. For a weekly class, decide how the local start time and time zone are represented, and where the recurrence ends.

If you publish a feed, keep the same UID for the same class when its details are updated. If you offer a downloadable calendar file, test importing it twice. Duplicate handling can differ between calendar apps and import flows, so check the actual clients your students use rather than assuming one universal behaviour.

3. Test the share path

Check the first week, the last week and a moved session in a real calendar app. Test on a phone configured for a different time zone to catch assumptions about local time. Keep the web view useful on its own too; some students will simply open the page and take a screenshot.

Start with readable timetable text, then add images only where they help. Use responsive image sizes and test a cold visit on a throttled connection. If the first lecture never appears because the page is waiting for a large image, the design has missed the point.

TRY WITH REAL INPUTS

Three timetable checks

  • Import a clean timetable with two sessions on one day.
  • Import an incomplete row and show exactly what needs attention.
  • Move a class and verify the updated event in a real calendar app.
  • Repeat the test after changing the phone's time zone.
